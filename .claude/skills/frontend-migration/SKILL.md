# Frontend Migration Placement

Migrate Vue 3 + Inertia files from another codebase into this project by (1) deciding
the correct destination folder, (2) placing the file with the right name, and
(3) rewriting its imports to this project's aliases and folder layout.

Both codebases use the same stack (Vue 3 SFCs + Inertia), so this is **classification
and re-wiring, not framework conversion.** Do not rewrite component logic or refactor
to conventions beyond fixing imports/paths unless the user explicitly asks.

## Source of truth

Each destination folder has a `README.md` in the repo describing exactly what belongs
there, with examples. These are authoritative — when a file is ambiguous, open the
relevant `resources/js/<Folder>/README.md` and match against its "What belongs / does
NOT belong here" sections before deciding. The `@/` alias maps to `resources/js/`
(see `tsconfig.json`).

## Destination map

| Destination | Holds | Signals it belongs here |
| --- | --- | --- |
| `resources/js/Pages/` | Inertia page views | Rendered by `Inertia::render('X')`; was in source `pages/` or `views/`; a full route screen |
| `resources/js/Layouts/` | Persistent layout shells | Has a default `<slot />`, name ends in `Layout`, was in source `layouts/` |
| `resources/js/Components/UI/` | Domain-agnostic primitives | Generic (Button, Input, Card, Modal); only props/slots/emits; NO Inertia/store/route imports |
| `resources/js/Components/Shared/` | Composed, app-aware components | Uses `@inertiajs/*`, stores, routes, or composes other components; domain-specific |
| `resources/js/Composables/` | `useXxx` composition fns | `.ts` file named `useXxx`, uses `ref`/`computed`/`watch`, returns state — no markup |
| `resources/js/Stores/` | Global reactive state | Pinia `defineStore`, or a `reactive()`/shared singleton used across components |
| `resources/js/lib/` | Pure utility functions | Stateless helpers (formatters, `cn()`); no Vue reactivity, no markup |
| `resources/js/types/` | TS types & ambient decls | `interface`/`type` definitions, `*.d.ts` module augmentations |

**Never place files in `resources/js/wayfinder/`, `resources/js/routes/`, or
`resources/js/actions/`.** These are generated by Wayfinder and gitignored. If a
migrated file imports route/action helpers from there, keep the import (see routes
below) and note that the user should run the Wayfinder generate step.

## Decision procedure

Work one file at a time. Read the file, then classify:

**`.vue` files**
1. **Page?** It's rendered as a route screen (came from `pages/`/`views/`, or the user
   says it maps to an `Inertia::render(...)` string). → `Pages/` (mirror any subfolder,
   e.g. `Users/Index.vue`).
2. **Layout?** It exists to wrap other pages — has a default `<slot />` and/or a
   `*Layout` name. → `Layouts/`.
3. **Otherwise a component.** Decide UI vs Shared:
   - **UI** only if it is genuinely generic and self-contained: driven purely by props,
     slots, and emits, with **no** imports from `@inertiajs/*`, no store access, no route
     helpers, and no dependence on other domain components.
   - **Shared** for everything else — anything that imports Inertia, reads a store, uses
     a route/URL, composes other components, or is tied to the app's domain.
   - When genuinely torn, prefer **Shared**. A misplaced primitive in Shared is harmless;
     a domain-coupled component in UI violates the layer boundary.

**`.ts` / `.d.ts` files**
1. **Composable** — filename `useXxx` and it uses Vue composition APIs → `Composables/`.
2. **Store** — global state (`defineStore` or shared `reactive` singleton) → `Stores/`.
3. **Types** — only type/interface declarations or `*.d.ts` → `types/`.
4. **lib** — pure, non-reactive helper functions → `lib/`.

## Naming

- Components, Pages, Layouts: **PascalCase** filenames (`UserCard.vue`, `Users/Index.vue`,
  `AppLayout.vue`). Rename kebab-case/camelCase source files accordingly.
- Composables: `useXxx.ts` (camelCase). Stores & lib: camelCase (`sidebar.ts`,
  `formatDate.ts`). Types: match the model (`user.ts`) or `*.d.ts`.
- Watch case-sensitivity: `Components`, `Pages`, `Layouts`, `Stores`, `Composables` are
  Capitalized; `lib`, `types`, `wayfinder` are lowercase. Getting case wrong breaks builds
  on case-sensitive filesystems even if it works on macOS.

## Fixing imports

After placing a file, rewrite its imports to this project's layout. Map common source
paths to their destination alias (adjust to whatever the source actually used):

| Source import (examples) | Rewrite to |
| --- | --- |
| `@/components/ui/...`, `~/components/ui/...`, relative `../ui/...` | `@/Components/UI/...` |
| `@/components/...`, `@/shared/...` | `@/Components/Shared/...` |
| `@/pages/...`, `@/views/...` | `@/Pages/...` |
| `@/layouts/...` | `@/Layouts/...` |
| `@/composables/...`, `@/hooks/...` | `@/Composables/...` |
| `@/stores/...`, `@/store/...` | `@/Stores/...` |
| `@/utils/...`, `@/helpers/...`, `@/lib/...` | `@/lib/...` |
| `@/types/...` | `@/types/...` |

Rules:
- Prefer the `@/` alias over deep relative paths (`../../`) for cross-folder imports;
  it's the project convention and survives future moves.
- Keep `@inertiajs/vue3` / `@inertiajs/core` imports as-is.
- For hardcoded route URLs or route helpers, prefer this project's Wayfinder helpers
  (`import { routeName } from '@/routes'` / `@/actions`). If the source used a different
  route helper, leave a clear `// TODO(migration): wire to @/routes` marker rather than
  guessing, and tell the user to regenerate Wayfinder.
- Match the **new** casing of every path segment you rewrite (`Components/UI`, not
  `components/ui`).
- Do not touch imports that already resolve correctly.

## Verifying placement

A file is placed correctly when its dependencies flow "downhill" through the layers:
`Pages → Layouts → Components/Shared → Components/UI`, with `Composables`, `Stores`,
`lib`, and `types` usable by any of them, and `Components/UI` importing none of them.
If a file you dropped in `Components/UI` imports a store, a route, or Inertia, that's a
signal it actually belongs in `Shared` — reclassify rather than leave the boundary broken.

## Reporting

After each migration (single file or batch), print a summary table so the user can see
and correct placement decisions:

```
| Source file            | → Destination                          | Notes                          |
| ---------------------- | -------------------------------------- | ------------------------------ |
| old/components/Btn.vue | resources/js/Components/UI/Button.vue  | renamed, imports rewritten     |
| old/pages/users.vue    | resources/js/Pages/Users/Index.vue     | route helper needs Wayfinder   |
```

Call out explicitly:
- Any file whose classification was ambiguous (and why you chose what you chose).
- Any import you could not confidently rewrite (left with a `TODO(migration)` marker).
- Any reference to generated route/action helpers that needs `wayfinder:generate`.

## Batch migrations

When migrating many files at once, do the leaf/shared dependencies first (types, lib,
Composables, Stores, UI), then the things that consume them (Shared, Layouts, Pages), so
that by the time you rewrite a Page's imports, its dependencies already live at their
final paths. Process each file through the same decision procedure; don't assume two
files from the same source folder land in the same destination — classify each on its
own merits.
